## Context

See proposal.md for why. What exists today:

- **Matriz**: `drizzle/seeds/data/progress-matrix.json` is generated by `scripts/build-progress-matrix.ts` from the workbook (objectives, *desafios* and links, v1.0) and loaded idempotently by `applyProgressMatrix` on every environment. The sheet's `objetivos educativos` tab has exactly the workbook's codes (174 objectives). The sheet's `desafios` tab has a v1.1 links column and flags five *desafios* that differ from v1.0.
- ***Desafios* in the database** hold the full official text with a literal `[Integração TEs,TEx,Clã]` marker at the end. The sheet keeps short titles and `integração` as separate columns.
- **Activity types** are plain editable rows (`activity_types`, `activity_activity_types`); the open change `activity-types-review` planned 10 types in two groups. The sheet instead has two tabs: `formatos` (8) and `focos` (10), and the activities tab has the columns `Formato`, `Foco`, `Foco secundário`.
- **Risk**: `physical_risk_level` and `psychological_risk_level` are text columns typed as `low | medium | high`; the sheet has five levels.
- **Loaders**: `scripts/load-baseline-activities.ts` with `baseline-map.ts`, `baseline-plan.ts`, `baseline-rich.ts` already parse the sheet's cells (durations, lists, per-division objective blocks, *desafio* codes, ODS) and write through `parseActivityWrite`/`createActivity`. It selects ~200 rows and has no stable key.
- **Activity rows in the sheet** (read for this design): `Fonte, Nome, Descrição, Instruções, Materiais, Mins, Grupo, Esforço físico, Local, Divisão, Risco físico, Risco psicológico, Mitigação física, Mitigação psicológica, Objetivos educativos (por divisão), Comportamentos a observar, ODS, Justificação dos ODS, Desafios, Imagem URL, Publicada, atividade_id (ATV-0001), …, link_fonte, duracao_min, duracao_max, variantes, campos_inferidos, confianca, estado, revisor`, then `Formato, Foco, Foco secundário`. Several helper columns in the sheet are auxiliary and are ignored.
- Counts per reference tab in the sheet: 8 formats, 10 focuses, 5 divisions, 2 locations, 3 effort levels, 3 group sizes, 5 risk levels, 17 ODS, 31 sources, 112 *desafios*.

## Goals / Non-Goals

**Goals:**
- One regenerable, reviewable path from the sheet to the database: reference data committed as JSON and loaded on every environment; activities loaded from a local snapshot.
- Nothing is guessed: unknown values are dropped and reported.
- Existing activities, programs and links survive the migration.

**Non-Goals:**
- No in-app upload (`admin-activity-excel-import`) and no staging tables (`bulk-activity-ingest`); both can reuse the mapping built here.
- No images (`Imagem URL` is stored as given or ignored; illustration is its own change).
- No change to the objective codes; the Regulamento differences are a recorded decision, not work.
- Hosted environments get reference data only; the ~1,080 activities are a local and test set (see D9).

## Decisions

**D1. Objectives stay as the workbook.** The earlier plan to follow the Regulamento where it differs is dropped. The generator and dataset are unchanged for objectives; `progress-matrix-objectives` records this and drops the 4A.2 / split / merge differences from its to-do list. The generator gets a new check that the sheet's objectives tab and the dataset have the same codes and texts, so a later edit of the sheet shows up as a diff instead of a silent drift.

**D2. *Desafios* from the sheet's `desafios` tab.** The generator takes the sheet export as an extra input. For each *desafio* code it reads the short title, the `integração` cell and the **v1.1** links column; the full text keeps coming from the workbook (the sheet only has the short one), with the `[Integração …]` marker removed by a single regular expression and the marker's divisions cross-checked against the `integração` cell (a mismatch fails the generator). The `igual?` column drives a report of the five differing *desafios*. *Alternative:* take titles from the sheet only. Rejected: the official full text is the thing leaders read in the detail view.

**D3. Integration as an array of divisions on the *desafio*.** `challenges.integration_age_groups` is a text array of age-group values (`scouts`, `adventurers`, `rovers`; `cub_scouts` for the entry *desafio* of the Alcateia). The sheet's cell uses the labels Alcateia, TEs, TEx, Clã, or `Alcateia, TEs, TEx, Clã` for all, and the generator maps them. *Alternative:* a join table. Rejected for 112 rows with no queries beyond "mandatory for division X".

**D4. Formats and focuses as two reference tables.** `activity_formats` and `activity_focuses` (`code`, `name`, `description`, `position`, `is_managed`), loaded from a committed JSON generated from the `formatos` and `focos` tabs and applied by the same idempotent loader pattern as the Matriz. `activities` gets `format_id`, `focus_id` and `secondary_focus_id` (nullable in the database so legacy rows survive, required by the write schema). *Alternative:* one `activity_types` table with a `group`. Rejected: the sheet has three distinct roles per activity (format, main focus, secondary focus), and foreign keys per role are clearer and cheaper to filter than a many-to-many with a role column. The counts shown in the filter come from the same foreign keys.

**D5. Old types keep their tables for now.** `activity_types` and `activity_activity_types` stay in the schema, hidden from the interface, so the migration is additive and reversible. A migration step maps existing links: Jogo, Quebra-Gelo, Reflexão, Técnica, Desafio and Aventura to the matching format; Criatividade, Cooperação and Liderança to the matching focus; Serviço has no equivalent and is reported. With several mapped types, the first by the former position wins and the rest are reported. Dropping the old tables is a later change.

**D6. Risk levels: widen the type, not the data.** The columns are plain text, so five stored values (`low`, `low_medium`, `medium`, `medium_high`, `high`) need a new typed list and labels only; the migration checks for a database constraint and, if one exists, replaces it. Existing values stay valid. The loader reads the label before the colon in the sheet cell ("Baixo a médio: …") and keeps the rest as the risk text.

**D7. Duration.** `approximate_duration_minutes` stays the number the program builder uses. New nullable `duration_min_minutes` and `duration_max_minutes` store the range; the loader fills the single value from `Mins` and the range from `duracao_min` and `duracao_max`, and reports rows where `Mins` lies outside the range.

**D8. Stable id and upsert.** `activities.external_id` (text, unique, nullable) holds `ATV-0001`. The loader looks up by it, compares the mapped values and writes only changes, and leaves rows without an external id alone. The existing duplicate check by normalised name and age group stays for the other import paths. Relations (divisions, locations, group sizes, objectives with behaviours, ODS with justification, *desafios*, source) are replaced as a set per activity inside one transaction, so a partial failure leaves the old version.

**D9. Activities stay local.** The snapshot and the loaded text are third-party content under mixed licences (the sheet's `fontes` tab lists them; some are "Sem termos indicados"). The snapshot file lives in git-ignored `data/`, the loader refuses non-local databases without an override, and nothing is committed as a fixture beyond a small synthetic sample. Whether any subset may go to Preview or Production is a separate licence decision.

**D10. Row policy.** All rows are read. Rows without a name, or whose name and external id both repeat an earlier row, are skipped with a reason. `Publicada` is respected by default; a `--approve-all` flag marks the loaded activities approved so the whole set shows in a local catalogue for tests. `estado`, `confianca`, `revisor`, `variantes`, `bruto_ids` and `campos_inferidos` are counted in the report but not stored.

**D11. Dirigentes.** The parser splits the objective and behaviour cells by division header and ignores any header that starts with "Dirigentes". The division list still keeps Dirigentes as a suitable audience.

**D12. Labels live in messages and tokens.** Division ages, branches and group-size labels come from `src/messages/*.json` and `src/lib/design/tokens.ts`; they change there, not in the database rows. The legacy `age_groups` and `group_sizes` tables (with "Pioneiros" and the old ranges) are checked for any remaining use; if none, they are left unreferenced and listed for a later clean-up rather than deleted here.

## Risks / Trade-offs

- **Sheet and workbook drift** → the generator compares the objectives tab with the dataset and fails on a difference.
- **A 1,080-row load pollutes the local database** → upsert by external id, dry run first, host guard, and `--replace` (with the references check) only when asked; the load needs approval each time.
- **Mapping old types loses information** (Serviço, extra types) → the migration reports what it could not map; the old links stay in the old tables.
- **Hosted databases have no activities from the sheet** → intended; reference data alone is loaded there, and format and focus are optional in the database so older rows stay valid.
- **Third-party content** → D9: local only until the licence decision.
- **Filter regression** → the type filter is replaced by format and focus filters; saved links with a `type` parameter are ignored without error.

## Migration Plan

1. Update `openspec/changes/progress-matrix-objectives` (decision) and mark `activity-types-review` as superseded (no deletion without asking).
2. Edit `drizzle/schema`, run `npm run db:generate` (ask first), review the SQL and commit it. The migration only adds tables and columns, plus the type mapping step.
3. Regenerate `progress-matrix.json` and the new datasets from the sheet export; review the report.
4. Local: after approval, `db:migrate`, then the reference loader, then the activity snapshot with `--dry-run`, then the real load into `scout_toolkit_dev` and `scout_toolkit_test`.
5. Preview and Production: the deploy applies the migration and loads the reference data; no activities.
6. Rollback: additive columns and tables; the old type tables are untouched, so an older build still works.

## Open Questions

- Should `Publicada = FALSE` rows stay unapproved in the normal (non-test) load? Default is yes; confirm when the first dry run shows how many there are.
- Should `estado` and `confianca` be kept as review fields for admins? The statistics change (`admin-revamp`) may want them; they are only counted for now.
